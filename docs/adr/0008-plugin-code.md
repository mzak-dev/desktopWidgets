# Plugin code: WebAssembly Code Sources in wasmi

A Plugin may carry one WebAssembly module that serves a Data Source, a **Code Source**. Its Widgets stay TOML and bind to it like any other source (`{weather.temp}`), and `on_click = "weather.refresh"` sends it an action. Code never builds element trees: the engine keeps owning layout, animation and the redraw scheduler (ADR-0004), and restyling stays a file edit.

**Runtime: wasmi**, a pure-Rust interpreter. Plugin code computes a few values every few seconds or minutes, so an interpreter is fast enough, and it keeps the exe small and the build simple. wasmtime would add a JIT the widgets do not need. wasmi has fuel metering but no epoch interruption, so each call gets a fuel budget and running out traps it. There is no WASI and no component model: a module imports only our `wf` functions.

**One thread per Plugin.** The UI thread never runs wasm and never waits for it. `value()` returns the last sample for that Instance, or the manifest's `[code.initial]` values with `loading = true`, and asks the worker for a fresh one. The worker tells the app which Instances changed, and only those redraw; waking by dependency would miss a Widget that shows an error card, because an error card records no dependencies. With nothing due, the worker blocks with no timer, so an idle desktop still costs nothing.

**The ABI is JSON in linear memory.** The host already converts between `Value` and JSON, it is easy to debug, and it does not depend on the language the module was written in. Parsing cost is irrelevant at these rates. The host copies each output out at once; results of host calls are parked on the host and fetched with `take`, so the host never calls into the guest from inside an import.

**Capabilities are declared.** `http` reaches only HTTPS hosts listed in `plugin.toml` (shown when installing, and again when an upgrade adds hosts); redirects go back to the module rather than being followed, and cookies and Windows credentials are never sent. `store_get`/`store_set` keep up to 1 MB per Plugin in `plugin-data/<id>.json`, which survives upgrades and goes on Remove. The network goes through WinHTTP, so there is no HTTP crate and the system proxy and certificates apply.

**Files are read-only, under declared folders.** `fs` lists, stats and reads text (1 MB a read, 16 MB a call) under folders `plugin.toml` names below the home folder (`fs_read = ["~/.claude"]`), shown at install like hosts, and under the folder a user picked in a param the manifest names (`fs_read_params = ["folder"]`). The pick counts only from the Instance's own settings, never a Widget's default, so a plugin cannot grant itself a folder. A path is checked against those folders as written before the disk is touched, so code cannot probe whether files exist elsewhere, and again after links are resolved, so a link cannot lead out. `..`, alternate data streams and names Windows would trim are refused, and Wayfinder's data folder, which holds every Plugin's saved data, is never readable. There is no write: a widget that needs to change files is not a plugin's job. This amendment was made for an `agents` widget reading `~/.claude`; system media and audio stay built-in Data Sources rather than capabilities.

**Limits.** Fuel per call, 32 MB of memory, capped input, output, body and log sizes, a request rate limit, and a refresh floor of 1 s (60 s after a network call). The next call waits at least 100 times the CPU the last one took. A trap throws the instance away and the next call starts fresh after a backoff that doubles up to 30 minutes; the Plugins page shows the error.

**`launch` from code.** A Widget that reads a Code Source may by default only `launch` `https://` links, so text from a server can never become a network path or a protocol handler for the shell to open. A Plugin whose values are local (an `agents` source reading `~/.claude`) may list more in `[code] launch`, shown at install: URL schemes (`vscode`), never `file`, `shell`, `search-ms`, script schemes or any `ms-` handler; and folders under home, inside which folders and documents open (checked again with links resolved) but programs, scripts and shortcuts never do. A Widget reading several Code Sources may open a target only if every one of them allows it, since any of them could have produced the text. A target with whitespace or quotes is refused, so it cannot turn into arguments for a handler.

Code never changes the user's params: those are settings the user owns. A module keeps its own per-Instance state, keyed by the Instance id it is given, and returns it in its values.
